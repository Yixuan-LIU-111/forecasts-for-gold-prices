> 依据：`docs/差距分析与开发清单.md`（2026-08-05 盘点）
> 目标定位：**构建可运行的 demo**，低成本优先，避免过度设计与高成本方案
> 文档性质：**仅决策建议，不修改代码**

---

## 0. 怎么读这份清单

- 本文只收录**待决策点（Decision Point）**，即「存在 ≥2 个合理方向、选错会让下游代码推倒重来」的岔路口；纯代码缺口（如「没写 FastAPI 服务」）属于工作项，不在此列。
- 严重度定义：
  - 🔴 **阻断级**——不定，下游核心子系统无法正确开工，或存在硬约束迫使必须选择。
  - 🟠 **高**——不定，某一主要子系统（数据层 / 模型层 / 应用层）会返工，或存在确定的代码级冲突。
  - 🟡 **中**——影响一致性 / 正确性，但有明确默认值，可边做边定。
  - 🟢 **低**——仅风险管控，不阻塞功能跑通。
- 每个决策点都给出 **demo 优先、低成本** 的解决建议，并含「负责人 / 预期耗时 / 实施步骤 / 关闭标准」，便于一次性拍板关闭。

## DP-1 · 端到端架构形态（微服务 vs 单体）

- **严重度**：🔴 阻断级（决定后续全部工程成本的最大杠杆）
- **具体内容**：方案 §6.1 / §13 规定「FastAPI 服务容器 + PostgreSQL 容器 + APScheduler + Docker Compose 双容器一键启动」。但 demo 目标是「跑起来看」，并非生产部署。需要决定：是严格按方案建双容器微服务骨架，还是降级为单机单体（Streamlit 直接调用模型与数据，数据存本地文件）。
- **影响范围**：`docker-compose.yml`、`Dockerfile`、`app/main.py`、`app/models/database.py`（5 张表）、`app/core/scheduler.py`、`requirements.txt` 几乎全部 Stage 1/2/4 工作项；以及 Postgres/uvicorn/sqlalchemy/apscheduler 等依赖。
- **阻断原因**：架构形态不定，Stage 1（基座）和 Stage 2（数据层）的 12+ 人天工作不知往哪写——若先按方案建 PG+FastAPI，后又改单体，等于白做。这是成本与返工的总开关。
- **建议解决（demo 优先、低成本）**：
  - **建议负责人**：产品 / 架构拍板（你）
  - **预期耗时**：0.25 天决策 + 0.25 天落文档
  - **实施步骤**：
    1. 拍板：demo 阶段**不引入 PostgreSQL、Docker、常驻 APScheduler**；采用「Streamlit 单体 + 本地函数调用 + 本地 JSON/CSV 数据」形态。
    2. 把 `demo_data/*.json`（已是完整 API 响应契约）作为前端与后端的**唯一数据交换格式**，后端逻辑直接产出同结构 JSON。
    3. 写一份 `docs/DEMO架构决策.md`（一页）：明确 demo 范围、砍掉的组件、以及「生产化时再补 FastAPI+PG」的升级路径。
  - **关闭标准**：存在书面决策；`docs/差距分析与开发清单.md` 中 A-5/A-6/B-1~B-2 等 PG/Docker 工作项被标记为「demo 阶段跳过」，后续不再为其投入。

## DP-2 · 时间粒度（30 分钟 vs 日频）

> ⚠️ **本决策已被用户硬约束覆盖**：预测窗口固定为未来 **30 分钟**（见 V2.0 §0.1 约束二），原「采用日频」建议作废。30 分钟数据获取作为数据工程风险（R2/R7）单独处置，不得降级为日频。以下原文保留作历史参考。

- **严重度**：🔴 阻断级（存在硬约束 R2，迫使必须选）
- **具体内容**：方案 §3.3 要求「分钟级采集、预测未来 30 分钟」；现状是日频数据、预测 30 个交易日。需要定调 demo 的时间粒度。
- **影响范围**：`app/core/data_collector.py`、`gold_prediction_model/features.py`（C-7 分钟级特征重构）、`train.py`（C-9 重训）、回测（E-10）。
- **阻断原因**：**yfinance 1 分钟数据仅回溯 7 天**（R2），2m/5m 约 60 天，与方案「3 个月分钟级回测 / 3 个月预加载」直接冲突。分钟级训练集规模不足，且 C-7 特征重构需 2 人天。不定粒度，数据层与模型层代码写了必返工。
- **建议解决（demo 优先、低成本）**：
  - **建议负责人**：数据 / 建模负责人
  - **预期耗时**：0.25 天
  - **实施步骤**：
    1. 拍板：demo 统一用**日频**数据，预测跨度定为「未来 N 个交易日」（建议 T+5，比 T+30 通常更可为）。
    2. 直接复用 `gold_prediction_model/data_loader.py` 现有日频管道，不再等分钟级数据。
    3. 在决策文档写明：此选择偏离方案 §3.3，待生产化再补分钟级（需先解决 R2 数据源）。
  - **关闭标准**：模型层与数据层确定以日频为输入；Stage 2 的 B-4 分钟级采集、Stage 3 的 C-7 分钟级重构被标记为「demo 阶段跳过」。

## DP-3 · 数据源 / 新闻源路线

- **严重度**：🟠 高（决定 Stage 2 的 8 人天怎么花）
- **具体内容**：方案 §3.2 指定价格走 yfinance（GC=F / DX-Y.NYB / ^VIX / ^IRX）、新闻走 NewsAPI；现状是自建 Playwright 爬虫抓新浪/CBOE/FRED 4 家官网 + 6 个独立宏观因子爬虫，且 `data/` 已有 17 个 JSONL/CSV 快照。需要定调 demo 用哪条数据路线。
- **影响范围**：`app/core/data_collector.py`（B-3/B-4/B-5/B-7）、历史预加载 B-8、新闻去重 B-6。
- **阻断原因**：
  - **NewsAPI 配额自相矛盾（R3）**：方案要求「每分钟轮询」= 1440 次/天，免费层仅 **100 请求/天**。

  - 现有 7 个爬虫工程质量整齐、无配额限制，是现成资产；但走 yfinance 还是走现有爬虫是完全不同的 8 人天。
- **建议解决（demo 优先、低成本）**：
  - **建议负责人**：数据负责人
  - **预期耗时**：0.5 天
  - **实施步骤**：
    1. 拍板：demo **直接用现有爬虫体系**——价格/因子用现有爬虫输出，新闻用现有 Playwright 4 站抓取；**砍掉 yfinance 与 NewsAPI 依赖**。

    3. 在方案 V1.1 中回填：数据源改用现有爬虫、新闻源为自建爬虫（R3 自然消解）。
  - **关闭标准**：demo 不依赖任何外部付费 API 密钥即可跑；B-4 的 yfinance、B-5 的 NewsAPI 工作项被替换/跳过。

## DP-4 · 模型情感入模 + demo 验收口径

- **严重度**：🟠 高（项目级 Go/No-Go，但 demo 可降级跑通）
- **具体内容**：方案核心卖点是「LLM 情感作为量化特征」（§9.4），但 `features.py:attach_sentiment_features()` 至今是空接口，从未有真实数据入模（R5）；实测严格防泄露下 AUC≈0.50、准确率低于朴素基线 0.6158（R1）。需要决定：① 是否先把情感特征真正入模验证；② demo 的验收是否以预测精度为门槛。
- **影响范围**：`gold_prediction_model/features.py`（C-8）、`train.py`（C-9）、信号归因（E-1）、准确率统计（E-9）、对外汇报口径。
- **阻断原因**：若以「准确率 > 60%」为 demo 门槛，则 C-9 模型攻关（3 人天且可能超支）不通过就全盘卡住；但项目最大卖点又确实没验证过，盲目投入 40 人天有打水漂风险。必须先把「卖点是否成立」与「demo 验收口径」两个决策分开。
- **建议解决（demo 优先、低成本）**：
  - **建议负责人**：建模负责人
  - **预期耗时**：0.25 天决策 + 1 天先导消融实验
  - **实施步骤**：
    1. **拍板 demo 验收口径**：demo 阶段验收 =「能跑出信号 + 可视化 + 链路完整」，**不**以预测精度为门槛；仪表盘对信号明确标注「演示用途」。
    2. **提前做 C-8 先导消融**（1 天，用现有日频数据即可，零额外采集成本）：把 `sentiment_mean_*` 真实喂入 `train.py` 重训，对比 AUC 是否高于 0.53。
    3. 据结果二选一：有增量 → 正常进入模型封装 C-10；无增量 → demo 照跑，模型效果作为独立议题后置，对外汇报统一以 `模型测试报告.md` 清洁结论为准。
  - **关闭标准**：① demo 验收口径书面确认（不以精度为门槛）；② C-8 消融有结论文档；③ 后续是否投入 C-9 已决策。

## DP-5 · 顶层 `import config` 冲突治理

- **严重度**：🟠 高（确定的代码级硬阻塞，低成本但必须先做）
- **具体内容**：`gold_prediction_model/*.py` 与 7 个 `*_scraper/config.py` 均使用顶层同名模块 `import config as C`（R4）。需要决定治理方式：改为包内相对导入，还是重命名为模块级 config。
- **影响范围**：`gold_prediction_model/*.py`、`dxy_scraper/ vix_scraper/ fred_scraper/ gpr_scraper/ epu_scraper/ dfii10_scraper/ investing_calendar_scraper/`、`app/core/*`（demo 单体下 app 会同时 import 模型与爬虫）。
- **阻断原因**：demo 单体架构要求 Streamlit 直接调用模型与爬虫。一旦 `app` 同时 import 两者，Python 模块缓存只会保留第一个被导入的 `config`，第二个包将读到错误配置甚至崩溃——这是确定会发生的冲突，且排查极隐蔽。
- **建议解决（demo 优先、低成本）**：
  - **建议负责人**：全栈开发
  - **预期耗时**：1.0 天（与差距清单 A-4 一致，但 demo 下必须前置）
  - **实施步骤**：
    1. 拍板治理方式：各包内 `import config as C` **改为包内相对导入**（`from . import config as C`），或重命名为 `gold_config` / `dxy_config` 等模块级名，彻底消除顶层同名。
    2. 在 `app/core/` 下新建 `imports.py` 桥接层：用 `importlib.util.spec_from_file_location` 按**绝对路径**显式加载模型与爬虫模块，绕开顶层名冲突，保证 demo 单体可同时调用。
    3. 验证：`python -c "from app.core.imports import load_model, load_scrapers"` 无冲突报错。
  - **关闭标准**：`app` 能同时 import 模型与任一爬虫且不报 `config` 冲突；`python -c "import app..."` 通过。
