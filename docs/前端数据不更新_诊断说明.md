# 前端数据不更新 · 诊断说明

> 排查目标：互联网新闻 / 爬虫数据的「获取与更新频率」配置位置、实际生效周期，
> 以及前端页面数据长期不刷新（停留在旧数据）的代码层面根因与修复建议。
> 排查日期：2026-08-06

---

## 0. 一句话结论

前端不刷新是**三层叠加**造成的，任何一层单独存在都会导致「数据不动」：

1. **后端调度器默认关闭** —— `demo_mode=True`（`.env` 为空取默认值），`main.py` 在 `demo_mode` 下**根本不启动 APScheduler**。没有采集/信号/新闻任务在后台跑，数据库只会在首次启动时灌入一次种子数据。
2. **前端没有任何轮询 / WebSocket 推送** —— `dashboard.html` 只在页面加载时调一次 `loadDashboard()`，没有任何 `setInterval` 周期性重新拉取数据（顶栏「实时刷新 5min」只是静态文案）。即便后端产生了新数据，前端也不会主动去拿。
3. **新闻情感落库存在「双写位置 + 字段不对齐」** —— 两条新闻管线（app 自带 `NewsAPI` 任务 vs `news_scraper_llm` CLI）写入不同的情感字段，且前端只读其中之一。即使把调度器打开，也需要先把管线对齐，否则抓到的真实新闻会显示成「中性」。

## 1. 数据流与更新频率架构

### 1.1 整体链路

```
[数据源] ──┬─ 因子/价格: app.core.collectors.base (yfinance / FRED / 新浪…)
           ├─ 新闻A(调度器): app.core.collectors.adapters.NewsCollector (NewsAPI) + app.core.sentiment.analyze_news
           └─ 新闻B(手动CLI): news_scraper_llm (Playwright 4站点) + qwen-turbo
                    │
            [APScheduler 后台任务]（仅 DEMO_MODE=false 时启动）
                    │ 周期：collect=60s / signal=300s / news=120s
                    ▼
            [SQLite: data/gold_predictor.db]
              news(内联 sentiment 字段) / sentiment(独立表) / market_data / factor_data / signals …
                    │
            [FastAPI GET /api/v1/news 等]  app/api/*.py → app/api/deps.py::serialize_*
                    │
            [前端] frontend/dashboard.html  fetch() 一次
                    ▼
             Plotly 渲染（仅首屏加载时，无再拉取）
```

### 1.2 更新频率配置位置 & 实际生效周期

| 配置项 | 位置 | 默认值 | 实际生效 | 说明 |
|---|---|---|---|---|
| `demo_mode` | `app/config.py:46` | `True` | **调度器不启动**（当前默认） | 关键开关；`main.py:64` 仅 `if not settings.demo_mode` 才 `start_scheduler()` |
| `collect_interval_seconds` | `app/config.py:60` | `60` | 仅调度器运行时：因子/价格每 60s | `scheduler.py:112` |
| `signal_interval_seconds` | `app/config.py:59` | `300` | 信号每 300s | `scheduler.py:116` |
| 新闻任务周期 | `scheduler.py:120` | `collect*2 = 120s` | 新闻每 120s | 依赖 `NEWSAPI_KEY` |
| `newsapi_key` | `app/config.py:55` | `""` | **空 → 新闻任务直接 return** | `scheduler.py:56` `if not settings.has_newsapi: return` |
| 调度器类型 | `scheduler.py:110` | `BackgroundScheduler` | 进程内线程，随 uvicorn 启停 | 无持久化、无跨进程 |

**生效判定**：当前项目根目录 `.env` 为空（无 `DEMO_MODE`/`NEWSAPI_KEY`/`OPENAI_API_KEY`），故全部取代码默认值 →
`demo_mode=True` + `newsapi_key=""`。
结论：**当前运行实例的调度器是关闭的**，且即使打开，新闻任务也因无 NewsAPI key 而空转；`news_scraper_llm` 这条真实管线是**手动 CLI，从未被任何调度器调用**。

## 2. 前端数据不刷新的具体根因（代码级）

### R1. 后端调度器默认不启动（首要原因）
- `app/main.py:58` `@app.on_event("startup")` → `init_app()`（灌种子数据）→
  `app/main.py:64` `if not settings.demo_mode: start_scheduler()`。
- `app/config.py:46` `demo_mode: bool = True`。根 `.env` 为空 → 默认 `True` → **`start_scheduler()` 不会执行**。
- 后果：后台永远没有采集/新闻/信号任务，数据库在首次启动后静止不变。所谓「实时」只停留在种子演示数据（如 `news` 表 10 条 `published_at` 均为 2026-07-30）。

### R2. 前端零轮询、无推送（次要但致命）
- `frontend/dashboard.html:987` 进程尾部只有 `loadDashboard();` 一次调用。
- 全文搜索 `setInterval` 仅出现于 `:611` `setInterval(tick,1000)`，而 `tick()` 只更新右上角时钟文本，**与数据无关**。
- 没有任何 `setInterval` 周期调用 `loadDashboard()/loadNews()/loadStats()…`，也没有 `WebSocket`/`EventSource`（路由层 `main.py` 无 `/ws`，各 router 无 WS handler）。
- 顶栏 `:278` `<span class="status">实时刷新 5min</span>` 是**写死的静态文案**，与真实行为不符。
- 后果：数据只在「页面加载」或「手动点击左侧导航按钮（触发 `showView`）」时拉取一次；之后后端即便有新数据，前端也看不到，除非刷新页面或点导航。

### R3. 新闻情感「双写位置 + 字段不对齐」（数据可见性 bug）
- **前端实际读取的字段**：`app/api/deps.py:159` `serialize_news` 取 `News.sentiment / sentiment_label / sentiment_score`（即 `news` 表的内联列）。
- **app 自带管线（正确但默认关闭）**：`app/core/scheduler.py:78-93` 在 `add(News(...))` 时同时写 `sentiment/sentiment_label/sentiment_score` 内联列 → 前端能正确显示情感。但此任务受 `has_newsapi` 守护（R1 已说明其关闭）。
- **news_scraper_llm 管线（真实可用但未被调度）**：`news_scraper_llm/db.py:211-217` 插入 `DbNews` 时**只写 title/url/source/published_at，不回填 news.sentiment 内联列**；情感仅写入独立的 `sentiment` 表（`:242-252`）。而前端根本不读 `sentiment` 表。
  后果：**手动跑 `news_scraper_llm` 抓来的新闻，在前端会全部显示成「中性」**（因为 `serialize_news` 对空值回退 `or "neutral"` / `or 0`）。
- 另：`app` 的 `Sentiment` 模型（`app/models/database.py:133-143`）只有 `news_id/score/topic/confidence/key_sentence/created_at`，**没有 `sentiment_label`**；而 `news_scraper_llm/db.py` 的 `DbSentiment` 又额外声明了 `sentiment_label/model_version/sentiment_mode/analyzed_at`。两者 `__tablename__` 同为 `"sentiment"`，靠 `news_scraper_llm/db.py` 的 `init_db()` 增量 `ALTER` 补齐列。若两个进程并发建表，以任一方的 metadata 为准，可能导致对方声明的列缺失——属潜在隐患。

### R4. 跨域 / 缓存不是主因（已排除）
- CORS：`app/main.py:40-45` `allow_origins=["*"]` → 不存在跨域拦截；且前端经 FastAPI 同源托管时 `API_BASE=""` 走相对路径，更无跨域问题。
- 前端无 `Cache-Control`/`ETag` 强缓存逻辑；问题不是「缓存未失效」，而是「根本没再发请求」。
- 数据绑定逻辑本身正确（字段名、颜色语义翻转 `INV` 映射均对齐），属 R2/R3 导致的「无新数据 / 数据字段缺失」。

## 4. 修复与排查建议（按优先级）

### P0 让后端真正开始更新
1. **打开调度器**：在根 `.env` 设置 `DEMO_MODE=false`（同时确认运行中的 uvicorn 已重启以读取新值）。
2. **配置新闻来源**：
   - 方案 A（走 app 自带管线）：填 `NEWSAPI_KEY=<你的key>`，并把 `app/core/collectors/adapters.py` 的 `NewsCollector` 接好；该任务会正确回写 `news.sentiment` 内联列（前端可见）。
   - 方案 B（走我们已验证的 `news_scraper_llm`）：**把 `news_scraper_llm` 接入调度器**（新增一个 `_job_news_scraper` 在 `scheduler.py` 中调用它），并保证它把情感**回填到 `news.sentiment` 内联列**，而不只是写 `sentiment` 表。
3. 验证：`curl http://127.0.0.1:8000/api/v1/news` 多次，观察 `published_at` 是否随时间变化；查看 uvicorn 日志是否出现「调度器已启动」「采集任务完成」「新闻采集完成，新增 N 条」。

### P1 让前端真正「刷新」
4. 在 `dashboard.html` 增加轮询：在 `:987` 之后加
   ```js
   setInterval(()=>{ if(document.querySelector('.view.active')?.dataset.view==='dashboard') loadDashboard(); }, 5*60*1000);
   setInterval(()=>{ if(document.querySelector('.view.active')?.dataset.view==='news') loadNews(); }, 60*1000);
   ```
   并把顶栏 `:278` 的静态「实时刷新 5min」改为真实状态（或接 WebSocket）。
5. （可选增强）后端加 SSE `/api/v1/stream` 推送「数据已更新」事件，前端监听后重拉——比纯轮询更省流量。

### P2 统一情感落库位置（消除 R3）
6. **单一事实来源**：让 `news_scraper_llm` 在 `persist()` 中也更新 `News.sentiment / sentiment_label / sentiment_score / topic / confidence / key_sentence` 内联列（或反之，改前端 `serialize_news` 去 JOIN `sentiment` 表取最新一行）。推荐前者——与 app 自带管线保持一致，前端零改动。
7. 收敛 `Sentiment` ORM 定义：把 `app` 与 `news_scraper_llm` 的 `sentiment` 表 schema 统一（共享同一模型或显式迁移），避免并发建表时列缺失。

### 验证清单
- [ ] `.env` 含 `DEMO_MODE=false` 且 uvicorn 已重启 → 日志见「调度器已启动」
- [ ] 日志出现「新闻采集完成，新增 N 条」（或 `news_scraper_llm` 被调度触发）
- [ ] `GET /api/v1/news` 多次返回不同 `published_at`
- [ ] 前端静置 5 分钟后，仪表盘新闻/行情自动变化（无需点导航）
- [ ] 真实新闻的情感标签非全中性（R3 修复后）
