# 「点时成金」技术栈选型评估报告

> 基于《需求规格说明书》、《用户故事清单》、《竞品分析报告》三份项目材料
> 评估目标：**构建可运行的 Demo**（非生产级系统）
> 文档版本：v1.0 | 创建日期：2026-06-26

---

## 一、项目约束与评估前提

### 1.1 Demo 阶段核心目标

| 维度 | 要求 |
|------|------|
| **功能范围** | 覆盖 P0 全部 + P1 部分功能（新闻采集、情感分析、时序预测、信号生成、Streamlit 仪表盘、回测） |
| **性能要求** | 信号生成延迟 < 3 秒，单用户即可，无需高并发 |
| **数据规模** | 3-6 个月历史数据 + 实时数据，分钟级粒度 |
| **团队规模** | 1-2 人，全栈开发 |
| **交付周期** | 2-4 周内产出可演示版本 |

### 1.2 六维度评估框架说明

| 维度 | 评分标准（1-10） | Demo 阶段权重 |
|------|-----------------|-------------|
| **开发效率** | 技术栈是否支持快速原型开发、组件复用度、调试便利性 | **25%** |
| **性能** | 数据处理吞吐、推理延迟、前端响应速度 | 10% |
| **可维护性** | 代码结构清晰度、模块化程度、后续升级成本 | 15% |
| **团队熟悉度** | 团队对技术的掌握程度、学习曲线、社区文档质量 | **20%** |
| **可行性** | 技术方案的成熟度、是否有成功案例、集成风险 | **20%** |
| **实施难度** | 环境搭建、组件集成、调试的复杂度（分数越高 = 越容易实施） | 10% |

> **加权逻辑**：Demo 阶段最看重"能不能快速做出来"（开发效率 25%）和"能不能跑通"（可行性 20% + 团队熟悉度 20%），性能和非功能需求优先级较低。

## 二、候选技术栈方案

### 2.1 方案一：Python 全栈·轻量 Demo 方案

**核心思路**：用最少的组件、最简单的架构，在最短时间内跑通全链路。

| 层次 | 技术选型 | 选型理由 |
|------|---------|---------|
| 语言 | Python 3.10+ | 数据科学首选，无需切换语言 |
| Web 框架 | FastAPI | 异步支持、自动生成 API 文档、开发快 |
| 可视化前端 | Streamlit | 纯 Python 写前端，零前端开发成本 |
| 数据库 | **SQLite** | 零配置、免安装、单文件存储 |
| 时序数据 | SQLite（或 CSV 文件） | Demo 阶段数据量小，无需时序数据库 |
| 机器学习 | **LightGBM** + Scikit-learn | 单模型快速验证，调参简单 |
| 深度学习 | 暂不引入 | Demo 阶段树模型足够 |
| LLM 调用 | **OpenAI API 直调** | 不引入 LangChain，减少依赖和调试成本 |
| 任务调度 | **APScheduler** | 单进程内调度，无需 Redis/Celery |
| 回测引擎 | **Pandas 手写回测** | 不引入 Backtrader，减少学习成本 |
| 部署 | **单 Docker 容器** | 一个 Dockerfile，一条命令启动 |

**架构图**：

```
┌──────────────────────────────────────────┐
│           单 Docker 容器                   │
│  ┌──────────┐  ┌──────────┐              │
│  │ FastAPI   │  │Streamlit │              │
│  │ (API服务) │  │ (仪表盘)  │              │
│  └─────┬─────┘  └────┬─────┘              │
│        │              │                    │
│  ┌─────┴──────────────┴─────┐              │
│  │      核心业务逻辑          │              │
│  │  ├── 数据采集 (requests)  │              │
│  │  ├── 情感分析 (OpenAI)    │              │
│  │  ├── 时序预测 (LightGBM)  │              │
│  │  ├── 信号生成 (APScheduler)│              │
│  │  └── 回测 (Pandas)       │              │
│  └─────────────┬─────────────┘              │
│        ┌───────┴───────┐                    │
│        │    SQLite     │                    │
│        │  (单文件数据库) │                    │
│        └───────────────┘                    │
└──────────────────────────────────────────┘
```

### 2.2 方案二：Python 全栈·工程化方案

**核心思路**：从 Demo 第一天就用生产级标准搭建，组件完备，后续无需重构即可平滑过渡到生产环境。

| 层次 | 技术选型 | 选型理由 |
|------|---------|---------|
| 语言 | Python 3.10+ | 数据科学首选 |
| Web 框架 | FastAPI | 异步高性能 |
| 可视化前端 | Streamlit（或 Grafana） | 可选 Grafana 做专业监控面板 |
| 关系数据库 | **PostgreSQL** | 生产级关系型数据库 |
| 时序数据库 | **ClickHouse** / **InfluxDB** | 专业时序存储，支持分钟级聚合查询 |
| 缓存 | **Redis** | 缓存热点数据，加速查询 |
| 机器学习 | LightGBM + **XGBoost** + **PyTorch** (LSTM/Transformer) | 多模型对比，A/B 测试框架 |
| LLM 调用 | **LangChain** + OpenAI / Claude 多模型 | 统一 LLM 调用接口，支持模型切换 |
| 任务调度 | **Celery** + Redis | 分布式任务队列，支持任务重试和监控 |
| 回测引擎 | **Backtrader** | 专业回测框架，支持滑点、手续费、多策略 |
| 部署 | **Docker Compose**（多容器）+ Nginx | 服务拆分，独立扩缩容 |
| 监控 | Prometheus + Grafana | 系统指标监控和告警 |

### 2.3 方案三：Python 全栈·推荐方案（平衡路线）

**核心思路**：在"快速出 Demo"和"工程化基础"之间取平衡点——组件数量适中，核心链路完整，预留扩展接口，后续可渐进式升级。

| 层次 | 技术选型 | 选型理由 |
|------|---------|---------|
| 语言 | Python 3.10+ | 数据科学首选 |
| Web 框架 | **FastAPI** | 异步支持、自动 OpenAPI 文档、Pydantic 数据校验 |
| 可视化前端 | **Streamlit** | 纯 Python，数据可视化组件丰富，开发效率最高 |
| 关系数据库 | **PostgreSQL** | 比 SQLite 更接近生产标准，Docker 一键部署无额外成本 |
| 时序数据 | PostgreSQL（带分区表） | Demo 阶段数据量 < 100 万行，PostgreSQL 完全胜任 |
| 机器学习 | **LightGBM** + **XGBoost** | 双模型对比，增加模型稳健性，学习成本低 |
| 深度学习 | 预留接口，暂不实现 | Demo 阶段树模型足够，架构预留 PyTorch 集成点 |
| LLM 调用 | **LangChain**（简化使用） | 统一 LLM 调用接口，方便后续切换模型；只用核心链式调用，不引入 Agent/VectorStore |
| 任务调度 | **APScheduler** | 单进程调度，无需 Redis 依赖，比 Celery 轻量得多 |
| 回测引擎 | **Backtrader** | 专业回测框架，比手写更可靠，学习成本可接受 |
| 部署 | **Docker Compose**（2 容器） | FastAPI + PostgreSQL 两个容器，Streamlit 可嵌入 FastAPI 或独立 |
| 前端增强 | Plotly（Streamlit 内置） | 交互式图表，无需额外前端库 |

- LangChain 版本更新频繁，需要注意依赖锁定

## 五、最终推荐方案

### 推荐：方案三 — Python 全栈·推荐方案（平衡路线）

**综合得分**：47/60（加权：43.5/60）

### 推荐理由

1. **Demo 阶段的最佳时间-质量平衡**：预计 1-2 周跑通全链路（新闻采集 → 情感分析 → 时序预测 → 信号生成 → 仪表盘展示 → 回测验证），比工程化方案快 50% 以上，同时比轻量方案多了可持续迭代的工程骨架。

2. **技术风险最低**：FastAPI + Streamlit + PostgreSQL + LightGBM + LangChain 是 Python 数据科学领域最成熟的组合，每个组件都有大量中文教程和社区支持，1-2 人团队几乎不会遇到"无解"的技术卡点。

3. **渐进式升级路径清晰**：Demo 验证通过后，可按需逐步升级：
   - 数据量增长 → PostgreSQL 分区表 → ClickHouse
   - 调度需求复杂 → APScheduler → Celery + Redis
   - 模型精度提升 → LightGBM → 加入 LSTM/Transformer
   - 前端需求增加 → Streamlit → React/Grafana

4. **双模型对比策略**：LightGBM + XGBoost 双模型在 Kaggle 竞赛中被反复验证优于单模型，投入产出比极高。同时可作为 A/B 测试框架的基础，验证不同模型在黄金 30 分钟预测场景下的表现差异。

5. **LangChain 简化使用策略**：仅用 `ChatOpenAI` + `PromptTemplate` + `StrOutputParser` 三个核心组件，避免引入 Agent、VectorStore、Memory 等复杂抽象。既保留了 LLM 模型切换能力（后续可换 Claude、国产模型），又不增加调试负担。

## 七、风险与应对

| 风险 | 严重程度 | 应对措施 |
|------|:--------:|----------|
| OpenAI API 调用成本过高 | 中 | 设置每日调用上限（如 $5/天）；对相同新闻缓存情感结果；预留本地小模型（如 FinBERT）替代方案 |
| LightGBM 在 30 分钟级别预测准确率不达标（<55%） | 高 | 双模型对比快速定位问题；增加特征工程迭代；若树模型确实不行，快速切换到 LSTM（方案预留了 PyTorch 接口） |
| 新闻 API 数据源不稳定或收费 | 中 | 优先使用免费 API（NewsAPI 免费层）；准备 RSS 爬虫作为备选；数据采集层抽象接口，方便切换数据源 |
| PostgreSQL 数据量增长后查询变慢 | 低 | Demo 阶段数据量 < 100 万行无此问题；后续可加分区表 + 索引优化 |
| LangChain 版本 breaking change | 低 | 锁定版本号（`poetry.lock`）；LangChain 简化使用仅依赖核心模块，breaking change 影响面小 |
