## 摘要（先看这一段）

仓库当前是**「两头厚、中间空」**的形态：

- **厚的两头**：前端仪表盘（Streamlit，约 2100 行，UI 完整度高）和离线模型实验（LightGBM+XGBoost 全流程 + 严谨的防泄露诊断报告）都已具备相当体量。
- **空的中间**：方案中作为系统骨架的 **FastAPI 服务、PostgreSQL 存储层、统一数据采集层、信号生成器、APScheduler 调度、Backtrader 回测、Docker 编排**——全部为 0 行代码。全仓库检索 `fastapi` / `sqlalchemy` / `postgres` / `apscheduler` / `backtrader` / `yfinance` 均无任何命中。

因此当前**不存在任何端到端链路**：仪表盘读的是本地静态 JSON，模型跑的是本地 CSV，两者之间没有连接。

除「缺失」外，还存在 **4 个方向性错配**，这些比缺失更需要优先决策，因为它们会决定后续代码怎么写：

| # | 错配 | 方案要求 | 当前实现 |
|:--:|------|---------|---------|
| 1 | **时间粒度** | 分钟级采集、预测未来 30 分钟（**用户硬约束，不可调**）| 日频采集、预测未来 30 个**交易日**（须重构为 30 分钟）|
| 2 | **数据源体系** | yfinance + NewsAPI | 新浪/CBOE/FRED/policyuncertainty + Playwright 抓 4 家官网 |
| 3 | **存储介质** | PostgreSQL 5 张表 | 散落在 `data/` 的 JSONL / CSV 文件 |
| 4 | **模型效果** | 方向准确率 > 60% | 实测严格防泄露下 AUC≈0.50、准确率**低于朴素基线** |

其中第 4 项是**项目级红灯**——`gold_prediction_model/reports/模型测试报告.md` 已诚实记录：T+30 准确率 0.4868（基线 0.6158）、AUC 0.4945。在补齐工程骨架之前，需要先回答「这个模型值不值得被工程化」。

另外发现 **2 处方案文档自身的内在矛盾**（NewsAPI 配额、yfinance 分钟级历史长度），详见第 5 章风险项 R2/R3，建议在开工前修订方案。

## 第 1 章 方案要点提炼

### 1.1 模块划分（方案 §6.1 / §18.2）

方案定义了 **6 个层次、单一 Python 应用容器 + PostgreSQL 容器**的结构：

| 层 | 模块 | 方案指定文件 | 职责 |
|----|------|-------------|------|
| 入口层 | FastAPI | `app/main.py` | HTTP 服务入口，6 个 REST 端点 |
| 入口层 | Streamlit | `app/dashboard/app.py` | 单页仪表盘 |
| 配置层 | 配置管理 | `app/config.py` | pydantic-settings 读环境变量 |
| 采集层 | 数据采集 | `app/core/data_collector.py` | yfinance + NewsAPI |
| 模型层 | 情感分析 | `app/core/sentiment.py` | LangChain + OpenAI |
| 模型层 | 时序预测 | `app/core/predictor.py` | LightGBM + XGBoost |
| 应用层 | 信号生成 | `app/core/signal_generator.py` | 规则引擎 + 防抖 + 降级 |
| 应用层 | 调度 | `app/core/scheduler.py` | APScheduler 每 5 分钟 |
| 应用层 | 回测 | `app/backtest/strategy.py` | Backtrader |
| 数据层 | ORM 模型 | `app/models/database.py` | SQLAlchemy 5 表 |
| 数据层 | 响应模型 | `app/models/schemas.py` | Pydantic v2 |
| 交付层 | 容器编排 | `docker-compose.yml` / `Dockerfile` | 双容器一键启动 |

### 1.2 核心功能清单（方案 §3.1）

**P0（必须实现）**：F01 新闻采集、F02 市场数据采集、F04 LLM 情感分析、F07 时序预测、F08 信号生成、F09 可视化仪表盘

### 1.3 关键流程

**主链路（方案 §10.1，每 5 分钟一轮，端到端 < 3 秒）**
```
APScheduler 触发
  → 1. 采集最新数据（yfinance 价格 + NewsAPI 新闻）
  → 2. 情感分析（新新闻走 LLM，已缓存的跳过）
  → 3. 特征组装（Pandas，4 类特征）
  → 4. 模型推理（LightGBM + XGBoost，p = 0.6·p_lgb + 0.4·p_xgb）
  → 5. 信号生成（方向 + 强度 + 仓位 + 归因 + 新闻引用）
  → 6. 写入 signals 表 + 推送仪表盘
```

**信号规则（方案 §10.1）**

| 条件 | 方向 | 仓位 |
|------|------|------|
| P > 0.60 且 置信度 > 0.55 | 看涨 | 中仓 |
| P > 0.70 且 置信度 > 0.70 | 看涨 | 重仓 |
| P < 0.40 且 置信度 > 0.55 | 看跌 | 中仓 |
| P < 0.30 且 置信度 > 0.70 | 看跌 | 重仓 |
| 其他 | 观望 | — |

**防抖**：连续 3 次方向反转 → 观望；VIX > 40 → 仓位降一档；置信度 < 0.55 → 观望
**降级**：LLM 不可用 → 规则引擎（关键词匹配），信号标记「低置信度」
**多空评分**：`score = 50 + 50·(P − 0.5)·confidence_weight + sentiment_bonus`

### 1.4 数据模型（方案 §8.2）

5 张表：`market_data`（时间戳+品种+价格+成交量）、`news`（URL 唯一约束用于去重）、`sentiment`（外键 news_id，score/topic/confidence/key_sentence）、`signals`（direction/probability/strength/position + JSONB factors + JSONB news_refs）、`backtest_results`（run_id UUID + JSONB metrics + JSONB trades）。

### 1.5 接口契约（方案 §11.2）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/signals/current` | 当前信号 |
| GET | `/api/signals/history` | 历史信号（分页） |
| GET | `/api/news/latest` | 最新新闻 + 情感标签 |
| GET | `/api/market/price` | 实时黄金价格 |
| GET | `/api/stats/accuracy` | 准确率统计 |
| POST | `/api/backtest/run` | 触发回测 |

统一响应 `{code, message, data}`；错误码 1001/1002/2001/2002/3001/3002/4001。

### 1.6 验收标准（方案 §16）

功能 8 项、性能 3 项（信号 < 3s、仪表盘加载 < 3s、连续运行 4h）、效果 3 项（方向准确率 > 60%、LLM 一致率 > 85%、信号带归因）、部署 4 项（`docker compose up` 一键启动）。

## 第 5 章 联调打通路径

### 5.1 推荐实施顺序

整体遵循 **「先决策 → 先立骨架 → 再通数据 → 再通模型 → 最后通前端」**，每个阶段都有可验证的硬性检查点。

**第 0 步 · 决策收敛（0.5 天）**
完成 D-1~D-5 五项决策并落成书面结论。这是硬前置——粒度和数据源没定，Stage 2/3 的代码写了会推倒重来。

**第 1 步 · 立骨架（2 天）** → 检查点：`docker compose up` 起来两个容器，`/docs` 可访问，数据库连得上
> A-1 → A-2 → A-3 → A-8 → A-5 → A-6，其中 A-4（导入冲突治理）可并行。
> 此时 FastAPI 只需一个 `/health` 端点，目的是**先把容器和数据库跑通**，避免后期集成时才发现环境问题。

**第 2 步 · 通数据（4 天）** → 检查点：**里程碑 M1**，`market_data` 与 `news` 表有 3 个月真实数据
> B-1 → B-2 → B-3 → B-4（价格）｜B-5+B-6（新闻，可并行）→ B-8（历史预加载）→ B-9
> B-7（存量爬虫接入）可延后到第 6 步，不阻塞主链路。

**第 3 步 · 通情感（2 天）** → 检查点：`sentiment` 表有数据，重复 URL 不重复调用 LLM
> C-1 → C-2 → C-3 → C-4 → C-5，C-6（鹰鸽）可并行。

**第 4 步 · 通模型（5 天，风险最高）** → 检查点：**里程碑 M2**，能对任意时间点输出 30 分钟上涨概率

**第 5 步 · 通信号（3 天）** → 检查点：`signals` 表每 5 分钟新增一条，含完整归因

### 5.4 三个必须尽早回答的问题

按对项目成败的影响排序：

1. **模型到底有没有预测力？**（R1 + R5）
   建议把 C-8「情感特征入模消融」从 Stage 3 中段提前为独立的**先导验证任务**，用现有日频数据先跑一版——只需 1 天，就能回答「加入 LLM 情感后 AUC 是否提升」。这个答案决定后续 40 人天投不投。

2. **分钟级数据从哪来？**（R2 + R7）
   yfinance 1 分钟只有 7 天历史，这个硬约束会同时打穿「3 个月回测」「3 个月历史预加载」「30 分钟预测训练集规模」三项要求。必须在写第一行采集代码前定好。

3. **保留哪套数据源体系？**（D-2 + D-3 + R3）
   现有 7 个爬虫工程质量整齐，是真实资产；但与方案指定的 yfinance/NewsAPI 完全是两条路。走哪条、混合到什么程度，直接决定 Stage 2 的 8 人天怎么花。
